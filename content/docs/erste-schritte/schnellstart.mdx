Wir bauen einen Job, der ein Bild in drei Größen umrechnet — inklusive der
Stelle, an der er absichtlich fehlschlägt, damit du siehst, was Wisp dann tut.

## Schritt für Schritt

<Steps>

<Step>
### Den Job schreiben

```ts title="jobs/bild-umrechnen.ts"
import { job } from 'wisp';

type Nutzlast = {
  bildId: string;
  groessen: number[];
};

export const bildUmrechnen = job('bild-umrechnen', {
  wiederholungen: 5,
  async run({ bildId, groessen }: Nutzlast, ctx) {
    const quelle = await speicher.lade(bildId);

    for (const breite of groessen) {
      ctx.log(`rechne ${bildId} auf ${breite}px`);
      const klein = await bild.skaliere(quelle, breite);
      await speicher.lege(`${bildId}/${breite}`, klein);
    }

    return { erzeugt: groessen.length };
  },
});
```

`ctx` ist der Job-Kontext: `ctx.log()` schreibt in das Protokoll dieses
Versuchs, `ctx.versuch` sagt dir, der wievielte Anlauf gerade läuft.
</Step>

<Step>
### Job bekannt machen

```ts title="jobs/index.ts"
export * from './bild-umrechnen';
```

Wisp lädt diese Datei beim Worker-Start. Was hier nicht exportiert wird,
kennt der Worker nicht — und ein `enqueue()` darauf schlägt sofort fehl statt
still zu verschwinden.
</Step>

<Step>
### Arbeit einreihen

```ts title="app.ts"
import { bildUmrechnen } from './jobs';

app.post('/hochladen', async (req, res) => {
  const bildId = await speicher.nimmEntgegen(req);

  await bildUmrechnen.enqueue({
    bildId,
    groessen: [320, 768, 1600],
  });

  res.status(202).json({ bildId });
});
```

<Callout title="202, nicht 200">
  Der Request ist fertig, die Arbeit nicht. `enqueue()` wartet nicht auf das
  Ergebnis — es kehrt zurück, sobald der Job im Speicher liegt.
</Callout>
</Step>

<Step>
### Laufen lassen

```bash
npx wisp worker --nebenlaeufig 4
```

```log
wisp  bereit — 1 Job registriert, Speicher: postgres
wisp  ▸ bild-umrechnen  #a91f  Versuch 1
      rechne 7c2e auf 320px
      rechne 7c2e auf 768px
      rechne 7c2e auf 1600px
wisp  ✓ bild-umrechnen  #a91f  1,4 s  { erzeugt: 3 }
```
</Step>

<Step>
### Fehlschlagen lassen

Nimm dem Prozess die Schreibrechte und reihe erneut ein:

```log
wisp  ▸ bild-umrechnen  #b30c  Versuch 1
wisp  ✗ bild-umrechnen  #b30c  EACCES: permission denied
wisp    → Wiederholung in 2 s (Versuch 2 von 5)
wisp  ▸ bild-umrechnen  #b30c  Versuch 2
wisp  ✗ bild-umrechnen  #b30c  EACCES: permission denied
wisp    → Wiederholung in 4 s (Versuch 3 von 5)
```

Die Abstände verdoppeln sich. Nach dem fünften Versuch landet der Job in der
Ablage für Gescheitertes — siehe
[Wiederholungen](/docs/konzepte/wiederholungen).
</Step>

</Steps>

## Was du jetzt weißt

- `job()` definiert **und** registriert
- `enqueue()` reiht ein und wartet nicht
- Fehlschläge sind normal; Wisp wiederholt mit wachsenden Abständen
- Der Worker läuft in einem eigenen Prozess

Als Nächstes lohnt sich [Jobs](/docs/konzepte/jobs) — vor allem der Abschnitt
darüber, warum Nutzlasten klein bleiben sollten.

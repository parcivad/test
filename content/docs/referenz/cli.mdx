```bash
npx wisp <befehl> [optionen]
```

Ohne Befehl zeigt Wisp die Hilfe. Jeder Befehl versteht `--config <pfad>`.

## `wisp worker`

Startet einen Worker und blockiert, bis er beendet wird.

```bash
npx wisp worker --nebenlaeufig 8 --warteschlangen standard,mails
```

| Option | Vorgabe | Bedeutung |
|---|---|---|
| `--nebenlaeufig <n>` | `4` | gleichzeitig ausgeführte Jobs |
| `--warteschlangen <a,b>` | `standard` | welche Schlangen bedient werden |
| `--stopp-frist <dauer>` | `30s` | Wartezeit auf laufende Jobs bei SIGTERM |
| `--metrik-port <port>` | — | Prometheus-Endpunkt unter `/metrics` |
| `--einmal` | aus | einen Stapel abarbeiten und beenden |

<Callout title="--einmal für Cronjobs">
  Mit `--einmal` läuft der Worker nicht dauerhaft, sondern arbeitet ab, was
  gerade da ist, und beendet sich. Damit kannst du Wisp aus einem
  Cron-Eintrag oder einem Kubernetes-`CronJob` heraus betreiben, ohne einen
  ständigen Prozess.
</Callout>

## `wisp status`

```bash
npx wisp status
npx wisp status --json          # maschinenlesbar
npx wisp status --wachen        # aktualisiert jede Sekunde
```

```text
Warteschlange   wartend  laufend  gescheitert  ältester wartender
standard             12        4            0  4 s
berichte              1        1            2  2 min
mails                 0        0            0  —
```

Die letzte Spalte ist die, auf die man schauen sollte: Wächst sie stetig,
kommen mehr Jobs herein als heraus.

## `wisp queue`

<Tabs items={['pause', 'resume', 'purge']}>

<Tab value="pause">

```bash
npx wisp queue pause berichte
```

Es wird nichts Neues mehr ausgegeben. Laufende Jobs laufen zu Ende. Der
Zustand steht im Speicher — ein Neustart hebt die Pause **nicht** auf.

</Tab>

<Tab value="resume">

```bash
npx wisp queue resume berichte
```

Nimmt die Ausgabe wieder auf. Wartende Jobs behalten ihre ursprüngliche
Reihenfolge und Priorität.

</Tab>

<Tab value="purge">

```bash
npx wisp queue purge berichte
npx wisp queue purge berichte --ja      # ohne Rückfrage
```

Verwirft alles Wartende. Laufendes bleibt unberührt, Gescheitertes auch.

<Callout type="error">
  Nicht rückgängig zu machen. `--ja` gehört nicht in ein Skript, das jemand
  versehentlich zweimal startet.
</Callout>

</Tab>

</Tabs>

## `wisp failed`

```bash
npx wisp failed list                   # was liegt in der Ablage
npx wisp failed list --job versenden   # nur ein Job-Name
npx wisp failed show a91f              # Protokoll aller Versuche
npx wisp failed retry a91f             # erneut einreihen
npx wisp failed retry --job versenden  # alle eines Namens
npx wisp failed drop a91f              # endgültig verwerfen
```

`retry` setzt den Versuchszähler zurück — der Job bekommt seine vollen
Wiederholungen erneut.

## `wisp migrate`

Legt die Tabellen an oder bringt sie auf den aktuellen Stand. Nur bei
Postgres nötig.

```bash
npx wisp migrate
npx wisp migrate --trocken     # zeigt das SQL, führt es nicht aus
```

<Callout title="Immer additiv">
  Migrationen fügen nur hinzu. Es gibt kein `DROP` und keine Umbenennung, also
  kannst du eine ältere Wisp-Version weiterlaufen lassen, während die neue
  schon migriert hat.
</Callout>

## `wisp enqueue`

Reiht von Hand ein — praktisch zum Ausprobieren.

```bash
npx wisp enqueue versenden '{"empfaenger":"a@example.org"}'
npx wisp enqueue bericht '{"monat":"2026-07"}' --verzoegerung 10m
```

<Callout type="warn">
  Die Nutzlast wird gegen nichts geprüft — die Typen aus `run()` existieren
  zur Laufzeit nicht. Ein Tippfehler im Feldnamen fällt erst im Job auf.
</Callout>

## Rückgabewerte

| Wert | Bedeutung |
|---|---|
| `0` | erfolgreich |
| `1` | allgemeiner Fehler |
| `2` | Konfiguration fehlt oder ist ungültig |
| `3` | Speicher nicht erreichbar |
| `4` | Migration nötig — `wisp migrate` ausführen |

`3` und `4` sind die, die man in einem Startskript unterschiedlich behandeln
will: Bei `3` lohnt ein erneuter Versuch, bei `4` nicht.

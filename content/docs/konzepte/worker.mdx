Ein Worker ist ein Prozess, der Arbeit aus dem Speicher holt und ausführt. Du
startest so viele, wie du willst — sie koordinieren sich über den Speicher,
nicht untereinander.

```bash
npx wisp worker --nebenlaeufig 8 --warteschlangen standard,berichte
```

## Der Takt

Ein Worker fragt nicht dauernd nach. Er holt einen Stapel, arbeitet ihn ab und
fragt erst dann wieder — mit wachsender Pause, wenn nichts da ist:

```text
Arbeit vorhanden  → sofort wieder holen
nichts vorhanden  → 200 ms, 400 ms, 800 ms … bis 5 s
```

Das hält die Last auf dem Speicher niedrig, wenn nichts los ist, und die
Latenz niedrig, wenn viel los ist.

## Nebenläufigkeit

`--nebenlaeufig` sagt, wie viele Jobs ein Worker **gleichzeitig** ausführt.
Der Standard ist 4.

<Callout type="warn" title="Nebenläufigkeit ist keine Parallelität">
  Node führt deinen Code in einem Thread aus. Acht nebenläufige Jobs helfen
  bei Wartezeit auf Netz und Datenbank — bei CPU-Arbeit wie Bildskalierung
  helfen sie nicht, sondern machen alle acht langsamer. Dafür brauchst du
  mehrere Prozesse.
</Callout>

Faustregel:

| Art der Arbeit | Einstellung |
|---|---|
| Warten auf HTTP oder Datenbank | 8–32 nebenläufig, ein Prozess |
| Rechenarbeit (Bilder, Krypto, Parsing) | 1–2 nebenläufig, mehrere Prozesse |
| Gemischt | trennen: eigene Warteschlange je Art |

## Warteschlangen zuweisen

Ohne Angabe nimmt ein Worker alles aus `standard`. Mit `--warteschlangen`
schränkst du ein:

```bash
# Prozess A: viele kurze Jobs
npx wisp worker --warteschlangen standard --nebenlaeufig 16

# Prozess B: wenige lange
npx wisp worker --warteschlangen berichte --nebenlaeufig 2
```

So kann ein Stau bei den Berichten die Mails nicht aufhalten. Mehr dazu unter
[Warteschlangen](/docs/konzepte/warteschlangen).

## Herunterfahren

Auf `SIGTERM` hört der Worker auf, Neues zu holen, und lässt Laufendes zu Ende
laufen — bis zur Frist aus `--stopp-frist` (Standard 30 s).

```log
wisp  SIGTERM — hole nichts Neues mehr
wisp  warte auf 3 laufende Jobs (Frist: 30 s)
wisp  ✓ 3 fertig, beende
```

Reicht die Frist nicht, wird `ctx.signal` ausgelöst und der Versuch als
Fehlschlag gewertet. Der Job ist nicht verloren: seine Pacht läuft ab, und der
nächste Worker nimmt ihn.

<Callout title="Für Container">
  Setz die Frist kürzer als die `terminationGracePeriodSeconds` deines
  Orchestrators. Sonst schießt der dir den Prozess ab, während Wisp noch
  wartet — der Effekt ist derselbe wie ein Absturz, nur unnötig.
</Callout>

## Beobachten

```bash
npx wisp status
```

```text
Warteschlange   wartend  laufend  gescheitert
standard             12        4            0
berichte              1        1            2
```

Für Metriken im Prometheus-Format lauscht der Worker auf `--metrik-port`:

```bash
npx wisp worker --metrik-port 9090
```

| Metrik | Bedeutung |
|---|---|
| `wisp_jobs_wartend` | Einträge, die auf einen Worker warten |
| `wisp_job_dauer_sekunden` | Histogramm der Laufzeiten je Job-Name |
| `wisp_versuche_gesamt` | Zähler, aufgeschlüsselt nach Ergebnis |
| `wisp_pacht_abgelaufen_gesamt` | wie oft ein Worker verschwunden ist |

Die letzte Zeile ist die interessanteste: Steigt sie, sterben dir Worker
mitten in der Arbeit.

Wirft `run()` einen Fehler, gilt der Versuch als gescheitert. Wisp wartet und
versucht es erneut — mit wachsendem Abstand.

## Der Standardverlauf

Bei `wiederholungen: 5`:

| Versuch | Abstand davor |
|---|---|
| 1 | — |
| 2 | 2 s |
| 3 | 4 s |
| 4 | 8 s |
| 5 | 16 s |

Der Abstand verdoppelt sich, plus ein zufälliger Zuschlag von bis zu 20 %.
Der Zuschlag verhindert, dass tausend gleichzeitig gescheiterte Jobs auch
gleichzeitig wiederkommen und denselben Dienst ein zweites Mal umwerfen.

```ts
export const abrufen = job('abrufen', {
  wiederholungen: 5,
  backoff: { art: 'exponentiell', basis: '2s', obergrenze: '5m' },
  async run() { /* … */ },
});
```

<Accordions type="single">

<Accordion title="backoff.art: 'exponentiell' (Standard)">
Verdoppelt den Abstand je Versuch. Richtig für alles, was von einem
überlasteten oder kurz ausgefallenen Fremdsystem abhängt.
</Accordion>

<Accordion title="backoff.art: 'fest'">
Immer derselbe Abstand. Sinnvoll, wenn du auf etwas wartest, das zu einem
bekannten Takt passiert — etwa einen Import, der stündlich läuft.
</Accordion>

<Accordion title="backoff.art: 'linear'">
Wächst um `basis` je Versuch statt zu verdoppeln. Der Mittelweg, wenn
exponentiell zu schnell zu lange Pausen erzeugt.
</Accordion>

</Accordions>

## Nicht alles ist wiederholbar

Ein Tippfehler in der Nutzlast wird beim fünften Mal nicht plötzlich richtig.
Wirf `FehlerEndgueltig`, um sofort abzubrechen:

```ts
import { job, FehlerEndgueltig } from 'wisp';

export const versenden = job('versenden', {
  wiederholungen: 5,
  async run({ empfaenger }: { empfaenger: string }) {
    if (!empfaenger.includes('@')) {
      throw new FehlerEndgueltig(`keine Adresse: ${empfaenger}`);
    }

    await mail.send(empfaenger);   // Netzfehler → wird wiederholt
  },
});
```

<Callout title="Die Trennlinie">
  Wiederholen hilft bei **vorübergehenden** Fehlern: Netz weg, Dienst
  überlastet, Sperre belegt. Bei **dauerhaften** Fehlern — kaputte Eingabe,
  fehlende Rechte, gelöschter Datensatz — kostet es nur Zeit und verdeckt die
  Ursache.
</Callout>

## Wenn alle Versuche weg sind

Der Job landet in der **Ablage** (`wisp_jobs` mit Status `gescheitert`). Dort
bleibt er, bis du ihn ansiehst — nichts wird automatisch gelöscht.

```bash
# was liegt da?
npx wisp failed list

# einen ansehen, inklusive Protokoll aller Versuche
npx wisp failed show a91f

# nach einem Fix erneut einreihen
npx wisp failed retry a91f

# alle eines Job-Namens
npx wisp failed retry --job versenden
```

## Benachrichtigen

```ts title="wisp.config.ts"
export default defineConfig({
  speicher: postgres({ url: process.env.DATABASE_URL! }),

  beiFehlschlag(job, fehler) {
    // läuft nach dem letzten Versuch, nicht nach jedem
    melde.an('#alarme', `${job.name} #${job.id}: ${fehler.message}`);
  },
});
```

<Callout type="warn">
  `beiFehlschlag` läuft im Worker-Prozess. Wirft der Haken selbst einen
  Fehler, wird er protokolliert und verschluckt — sonst würde ein kaputter
  Alarmweg dir den Worker mitreißen.
</Callout>

## Aufräumen

Erledigte Jobs bleiben standardmäßig sieben Tage liegen, damit du nachsehen
kannst, was gelaufen ist:

```ts
export default defineConfig({
  aufbewahrung: {
    erledigt: '7d',
    gescheitert: '30d',
  },
});
```

Gescheiterte länger als erledigte — sie sind die, die man später noch braucht.

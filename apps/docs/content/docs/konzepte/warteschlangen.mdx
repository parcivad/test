Eine Warteschlange ist ein Name, sonst nichts. Sie existiert, sobald ein Job
sie benennt, und verschwindet, wenn keiner sie mehr nutzt.

```ts
export const bericht = job('monatsbericht', {
  warteschlange: 'berichte',
  async run() { /* … */ },
});
```

## Wozu trennen

Damit langsame Arbeit schnelle nicht aufhält. Liegen 500 Berichte à zwei
Minuten in derselben Schlange wie die Anmelde-Mails, warten die Mails
zwanzig Stunden.

```text
eine Schlange:        [bericht][bericht][mail][bericht][mail] …
                       └── die Mails hängen hinter den Berichten

zwei Schlangen:       berichte: [bericht][bericht][bericht] …
                      standard: [mail][mail] …
                       └── eigener Worker, eigenes Tempo
```

<Callout title="Faustregel">
  Trenne nach **Dauer**, nicht nach Fachbereich. „Alles von der Rechnung“ ist
  eine schlechte Schlange, „alles, was länger als eine Minute läuft“ ist eine
  gute.
</Callout>

## Priorität

Innerhalb **einer** Schlange entscheidet `prioritaet` — höher zuerst:

```ts
await mahnung.enqueue({ kundeId }, { prioritaet: 10 });
await newsletter.enqueue({ kundeId }, { prioritaet: 0 });
```

<Callout type="warn" title="Priorität wirkt nicht über Schlangen hinweg">
  Ein Job mit Priorität 100 in `berichte` wird nicht vor einem Job mit
  Priorität 0 in `standard` ausgeführt. Wer das erwartet, braucht keine zwei
  Schlangen, sondern eine.
</Callout>

## Die Pacht

Wenn ein Worker einen Job holt, bekommt er ihn nicht — er *pachtet* ihn, für
eine begrenzte Zeit. Solange die Pacht läuft, ist der Job für alle anderen
unsichtbar.

```text
t=0     Worker A pachtet Job #a91f bis t=30
t=12    Worker A stirbt
t=30    Pacht läuft ab, Job wird wieder sichtbar
t=31    Worker B pachtet Job #a91f bis t=61
```

Deshalb geht kein Job verloren, wenn ein Worker abstürzt — und deshalb kann
ein Job trotzdem zweimal laufen. Beides folgt aus demselben Mechanismus.

### Verlängern bei langer Arbeit

Läuft ein Versuch länger als die Pacht, verlängert Wisp sie automatisch,
solange der Prozess lebt. Blockiert dein Code jedoch die Ereignisschleife,
kommt die Verlängerung nicht durch:

```ts
// blockiert — die Pacht kann nicht verlängert werden
const ergebnis = riesigeBerechnungSynchron(daten);

// gibt die Schleife frei
const ergebnis = await inWorkerThread(() => riesigeBerechnungSynchron(daten));
```

<Callout type="error" title="Das Symptom">
  Ein Job läuft scheinbar doppelt, obwohl nur ein Worker existiert. Ursache
  ist fast immer synchrone Rechenarbeit, die länger dauert als die Pacht: Wisp
  hält den Job für tot und gibt ihn frei, während er noch rechnet.
</Callout>

## Anhalten und leeren

```bash
# nichts Neues mehr ausgeben, Laufendes fertigstellen
npx wisp queue pause berichte

# weiter
npx wisp queue resume berichte

# alles Wartende verwerfen (Laufendes bleibt unberührt)
npx wisp queue purge berichte --ja
```

`purge` ist endgültig und fragt deshalb nach. Mit `--ja` fragt es nicht — nimm
das nicht in ein Skript, das jemand versehentlich zweimal startet.

## Verzögert einreihen

```ts
// in zehn Minuten
await erinnerung.enqueue({ id }, { verzoegerung: '10m' });

// zu einem festen Zeitpunkt
await bericht.enqueue({ monat }, { starteAm: '2026-09-01T03:00:00Z' });
```

Verzögerte Einträge liegen in derselben Schlange, sind aber bis zu ihrem
Zeitpunkt unsichtbar. Sie tauchen in `wisp status` unter `wartend` auf, nicht
unter `laufend`.
